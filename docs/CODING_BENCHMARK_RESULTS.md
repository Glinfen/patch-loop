优化前 CSV 任务已产生正确补丁并通过独立测试，但随后连续调用未列入精确白名单的安全诊断命令，触发重复错误保护，Runtime 状态为 `failed`。优化后只扩展两类只读或编译诊断：`git status` 和使用仓库内相对路径的 `python -m compileall`；绝对路径、路径穿越、任意 Python 和其他 Shell 命令仍被拒绝。

CSV 任务的步骤从 15 降至 14，工具调用从 23 降至 21，Runtime 状态由 `failed` 变为 `completed`。整体时延、Token 和费用没有同步下降，说明单轮模型采样波动大于本次局部策略收益，不能用两轮数据声称全局效率改善。

## 工程修复

- fixture 复制现在忽略与仓库指纹相同的 `.patchloop`、pytest cache 和 Python bytecode 目录，避免 Windows 权限缓存污染运行。
- CLI 原生读取目标根目录 `.env`，兼容 `LLM_*` 与 `DEEPSEEK_*` 变量，显式进程环境变量优先。
- `run_command` 从僵硬的完整命令字符串集合改为受约束的安全语法，保留相对路径和参数校验。

## 证据与限制

原始任务级报告位于 `benchmarks/results/code_benchmark_latest.json` 和 `benchmarks/results/code_benchmark_optimized.json`。每项报告包含测试输出、变更范围、步骤、工具调用、Token、费用、时延和本地轨迹路径。

当前数据只覆盖 6 个公开、体量较小的 Python 任务，每种配置仅采样一次。100% 只代表该固定套件的两轮结果，不代表未知仓库上的通用修复率。下一阶段应增加隐藏测试、失败任务、跨文件修改和至少 3～5 次重复采样，并优先优化目前偏高的上下文与工具调用成本。
