# PatchLoop 实施计划

## 1. 实施原则

- 先打通最小闭环，再优化单个模块。
- 每项能力都需要自动化验收方式。
- 所有性能结论必须来自固定任务集和可复现配置。
- 优先完成能体现技术判断的核心系统，延后多 Agent、复杂前端等展示性功能。
- 每周都保持主分支可运行，并留下可演示增量。

## 2. 建议技术栈

| 模块 | 推荐方案 | 选择原因 |
| --- | --- | --- |
| 主语言 | Python 3.12 | AI 生态成熟，适合快速构建 Agent Runtime |
| CLI | Typer + Rich | 易构建结构化命令和流式终端体验 |
| 数据模型 | Pydantic | 统一模型输出、工具参数和事件结构校验 |
| 模型适配 | 自建轻量 Provider 接口 | 避免核心运行时绑定单一模型厂商 |
| 状态存储 | SQLite + SQLAlchemy | 本地优先、易调试，后续可迁移 PostgreSQL |
| 代码解析 | tree-sitter 或 Python AST | 提取符号、引用与代码块边界 |
| 文本检索 | ripgrep | 快速、稳定，适合作为基础召回 |
| 语义检索 | 可插拔 Embedding + FAISS/Qdrant | 支持混合召回和对比实验 |
| 沙箱 | Docker，Windows 开发可提供受限进程降级 | 隔离依赖、网络与文件系统 |
| 可观测性 | OpenTelemetry + JSONL | 标准化 Trace，并方便离线评测 |
| 测试 | pytest | 单元、集成和端到端测试统一 |
| 质量工具 | Ruff + mypy + pre-commit | 建立稳定的工程基线 |

原则上先使用简单、可控的自研状态机，不在首版引入重量级 Agent 框架。这样更容易展示核心机制、调试执行路径并完成针对性优化。

## 3. 总体架构

```text
用户 / CLI
    │
    ▼
任务服务 ─────── 预算与权限策略
    │
    ▼
Agent Runtime ── Planner / Executor / Reviewer
    │                 │
    │                 ├── 短期上下文与任务记忆
    │                 └── 检查点与失败恢复
    ▼
Tool Gateway ─── 文件 / 搜索 / 补丁 / Shell / Test / Git
    │
    ├── Repository Intelligence
    │      └── 文本索引 / AST 符号图 / 语义索引
    │
    └── Sandbox & Approval

所有模块 ────── Event Store / Trace / Metrics / Replay
```

### 3.1 核心模块职责

| 模块 | 职责 |
| --- | --- |
| Task Service | 创建任务、维护状态、取消/恢复任务、管理配置 |
| Agent Runtime | 驱动状态机，选择下一步动作并处理模型输出 |
| Context Engine | 检索、排序、裁剪上下文，管理摘要和证据引用 |
| Tool Gateway | 统一工具协议、参数校验、超时、重试和结果截断 |
| Sandbox | 隔离命令、限制路径和网络、记录资源使用 |
| Event Store | 持久化任务、步骤、工具结果、补丁和指标 |
| Evaluator | 批量运行任务、执行判定、聚合指标和生成报告 |

## 4. 核心数据与接口设计

实施前先稳定以下领域模型：

- `Task`：用户目标、仓库、状态、预算、创建时间和最终结果。
- `Plan`：步骤、依赖关系、状态和完成证据。
- `AgentStep`：模型输入摘要、决策、动作、观察和错误。
- `ToolCall`：工具名、结构化参数、权限级别、结果和耗时。
- `Checkpoint`：当前计划、工作区快照、上下文摘要和预算消耗。
- `Artifact`：补丁、测试报告、轨迹文件和最终报告。

模型不得直接拼接 Shell 命令后绕过系统执行。所有动作必须通过带类型校验的工具协议进入 Tool Gateway。

## 5. 十周实施路线

任务：

- 确定首版只支持 Python 仓库和 CLI。

- 定义 Task、AgentStep、ToolCall 等核心数据模型。
- 准备 3 个极小的样例仓库和任务，作为贯穿开发的冒烟测试。

- 可安装的空骨架。
- 架构决策记录 ADR-001。
- CI 可运行 lint、type check 和 unit test。

退出标准：一次提交能够通过全部质量检查，CLI 能创建并读取一个任务。

### 第 1 周：模型与工具协议

- 实现只读工具：列目录、读文件、全文搜索、读取代码片段。
- 使用假模型完成确定性的单元测试。

退出标准：模型可以根据任务连续调用多个只读工具，所有调用被结构化记录。

## 7. 测试策略

### 7.1 单元测试

- 状态迁移和预算计算。
- 模型结构化输出解析。
- 工具参数、路径和权限校验。
- Patch 应用与冲突处理。
- 检索排序和上下文裁剪。
- 错误分类及重试策略。

### 7.2 集成测试

- Agent Runtime 与假模型、工具、数据库协同。
- Docker 沙箱内的命令执行和资源限制。
- 索引构建、增量更新和混合检索。
- 任务暂停、进程退出和恢复。

### 7.3 端到端测试

- 在固定样例仓库执行真实缺陷修复。
- 验证最终补丁、测试结果、轨迹和报告。
- 对失败任务确认仓库不会留下越权或半完成变更。

### 7.4 非确定性控制

- 单元测试不依赖真实模型，使用录制响应或确定性 Fake Provider。
- 真实模型评测固定模型版本、温度、提示词和最大预算。
- 核心实验至少运行三次，报告均值与波动，而非挑选最佳结果。

## 8. 评测设计

### 8.1 任务分层

| 难度 | 特征 | 建议数量 |
| --- | --- | ---: |
| Easy | 单文件修改、错误位置明显 | 10 |
| Medium | 跨 2～5 个文件，需要定位调用关系 | 15 |
| Hard | 需求有歧义、跨模块、需要多轮调试 | 5+ |

任务来源可包括自建样例、固定版本开源仓库中的已修复 Issue，以及规模可控的公开基准子集。必须保存合法来源、仓库提交版本和测试判定方式。

### 8.2 核心指标

- `resolved_rate`：通过任务全部隐藏测试的比例。
- `first_pass_rate`：第一次提交补丁即通过的比例。
- `tool_success_rate`：工具正常返回且满足协议的比例。
- `mean_steps`：成功任务平均 Agent 步数。
- `mean_latency`：平均端到端时延。
- `mean_tokens` 与 `mean_cost`：单任务资源消耗。
- `recovery_rate`：出现可恢复错误后最终成功的比例。
- `context_precision`：被加入上下文的片段中，与最终修改或证据相关的比例。

### 8.3 必做对比实验

- 完整系统 vs. 一次性生成补丁。
- 完整系统 vs. 无显式规划。
- 混合检索 vs. 纯关键词检索。
- 有上下文压缩 vs. 仅保留最近消息。
- 有失败反思 vs. 固定策略重试。

## 9. 安全设计清单

- 默认只允许访问指定仓库目录。
- 路径规范化后再次检查是否越界，防止 `..` 和符号链接逃逸。
- Shell 使用参数化执行，设置超时和输出上限。
- 默认禁止联网、提权、后台常驻进程和访问宿主机凭据。
- 写操作前保留工作区状态，任务结束后输出完整 diff。
- 删除、批量覆盖、安装依赖和修改 Git 历史需要显式批准。
- 日志对 API Key、Token、私钥和 `.env` 内容脱敏。
- 模型读取仓库内容时考虑 Prompt Injection，将代码与系统指令分离。

## 10. 每周工程节奏

每周保持以下固定输出：

1. 周初确定一个可演示的纵向目标和验收测试。
2. 先补测试与接口，再实现功能。
3. 周中运行样例任务，保存成功和失败轨迹。
4. 周末更新指标、ADR、风险清单和演示录像。
5. 只在已有指标表明瓶颈时做性能优化。

## 11. 风险与应对

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| 项目范围过大 | 无法按期形成完整作品 | 锁定 Python + CLI + 单 Agent，扩展项严格后置 |
| 模型结果不稳定 | 测试偶发、结论不可信 | Fake Provider、固定配置、多次运行、报告波动 |
| API 成本过高 | 无法持续评测 | 预算上限、缓存、分层模型、先用小任务调试 |
| 沙箱在不同平台表现不一致 | 演示难复现 | Docker 作为标准环境，本地受限进程仅作开发降级 |
| 评测集泄漏或过拟合 | 指标缺乏说服力 | 保留隐藏测试与留出集，记录任务来源和版本 |
| 只展示 Happy Path | 面试时暴露可靠性不足 | 保存失败轨迹，公开限制和错误分类报告 |
| 过早构建多 Agent | 系统复杂但基础成功率低 | 达成单 Agent Portfolio 指标后再评估 |

## 12. 阶段验收门槛

### MVP Gate

- 3 个样例任务端到端通过。
- 核心模块单元测试覆盖关键分支。
- 命令执行受限，所有修改有 diff。
- 任务轨迹可查询，失败可解释。

### Beta Gate

- 10 个以上任务稳定批量执行。
- 支持检查点恢复和完整预算控制。
- 混合检索有优于关键词基线的数据。
- 安全测试覆盖路径逃逸、危险命令和敏感信息。

### Portfolio Gate

- 30 个以上任务完成三轮评测。
- 成功率、成本、时延和错误分布均有报告。
- 至少完成三项消融或基线对比。
- 快速开始、架构文档、演示视频和技术文章齐全。
- 简历中的每一个数字都能由脚本和原始结果复现。
