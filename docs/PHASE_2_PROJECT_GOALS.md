# PatchLoop 第二阶段项目目标

## 1. 阶段定位

PatchLoop 第一阶段建立了单 Agent 执行闭环、工具协议、持久化、代码检索、记忆、缓存诊断和本地评测基础。第二阶段不再以增加独立算法模块为主要目标，而是把这些能力组合成一个开发者可以持续使用、可以控制、可以恢复且结果可信的本地 Coding Agent。

第二阶段的目标不是在功能数量上追平 Codex 或 Claude Code，而是完成一条可靠的真实工作流：用户在真实仓库中启动会话，持续追加要求，审查高风险动作，允许 Agent 在隔离工作区修改和验证代码；程序重启后会话能够继续，模型 Provider 可以替换，Skill 可以按需安装和加载，最终结果可以通过 diff、测试和 Trace 审计。

阶段完成后，PatchLoop 应从“研究型 Agent Runtime 原型”进入“具备日常试用价值的本地单 Agent”。

## 2. 目标用户与核心场景

目标用户：

- 希望在本地或私有仓库中使用 Coding Agent 的个人开发者。
- 需要替换模型供应商或接入企业兼容接口的研发团队。
- 希望研究 Session、工具使用、记忆和人机协作机制的 Agent 开发者。

核心场景：

- 在已有仓库中通过多轮对话澄清并完成一个 Issue。
- 在执行过程中追加约束、纠正方向、中断任务并在重启后继续。
- 审查文件写入、命令、联网和依赖安装请求，并以有限范围授权。
- 在隔离 worktree 中修改代码、运行测试、查看 diff、撤销或提交结果。
- 为特定技术栈安装并按需加载 Skill，不把全部说明永久放入上下文。
- 在不同 Provider 或本地兼容服务间切换，而不改写 Runtime 主流程。
- 对失败任务回放模型、工具、审批、文件和测试事件，定位真实失败原因。

## 3. 第二阶段 Project Goals

### S2-G1：建立持久化交互 Session

Session 必须成为用户与 Agent 的长期交互边界，而不是一次性的 `run` 调用。一个 Session 可以包含多轮用户输入、一个或多个连续任务、模型和工具事件、待审批动作、上下文压缩与恢复状态。

目标结果：

- 支持创建、列出、进入、继续、中断、恢复和结束 Session。
- 用户可以在 Agent 运行前后追加消息、纠正目标和要求继续工作。
- 进程退出或机器重启后，可以恢复对话、未完成计划和待处理控制状态。
- 已确认的写操作和工具结果不会在恢复后重复执行。
- Session、Task、Turn、Agent Step 和 Checkpoint 具有明确且版本化的关系。

### S2-G2：形成可替换的 Provider 生态

Provider 抽象必须由多个协议实现验证，而不是只服务 DeepSeek 的兼容格式。

目标结果：

- 支持 DeepSeek/OpenAI-compatible Chat Completions、OpenAI Responses 和 Anthropic Messages 等至少两类独立协议族。
- 支持一个本地或企业 OpenAI-compatible 服务路径。
- 统一处理流式输出、reasoning、工具调用、用量、缓存字段、取消、超时、重试和错误分类。
- 通过能力声明决定工具、并行调用、上下文、缓存和结构化输出策略。
- Provider 切换不会改变任务权限、安全边界和持久化语义。

### S2-G3：实现可恢复的人机审批控制面

Approval 必须是持久化状态机，而不是同步 CLI 中的一次布尔询问。

目标结果：

- 高风险动作进入明确的 `waiting_for_approval` 状态并可跨进程恢复。
- 支持批准一次、在限定范围内批准、修改参数后批准和拒绝。
- 授权范围可以限定工具、路径、命令、网络目标、时限和 Session。
- 拒绝结果作为结构化观察返回 Agent，使其能够选择安全替代方案。
- 所有审批决定可审计、可回放且不能被 resume 或 Provider 切换绕过。

### S2-G4：建立安全、按需加载的 Skills 系统

Skills 应扩展 Agent 的工作方法和领域知识，但不能隐式扩大权限。

目标结果：

- 支持内置、用户级和项目级 Skill 的发现、安装、更新、禁用与版本识别。
- Skill 可以包含说明、脚本、模板和参考资料，并通过统一清单声明入口与依赖。
- 根据任务和显式调用按需加载 Skill，避免全部内容进入 system prompt。
- Skill 内容按信任来源处理；项目内 Skill 默认不能自行获得执行、联网或仓库外访问权限。
- Trace 记录 Skill 的选择理由、版本、加载资源和实际执行动作。

### S2-G5：把 Sandbox 提升为可验证的隔离边界

当前本地白名单和 Docker 限制只能称为安全护栏。第二阶段需要定义威胁模型，并用攻击性测试证明支持范围内的隔离属性。

目标结果：

- 明确区分隔离 Sandbox 与非隔离 local fallback，CLI 不使用误导性安全表述。
- 隔离文件系统、环境变量、网络、进程树、系统调用和资源使用。
- 防御路径穿越、符号链接或 junction、TOCTOU、后台进程、输出洪泛和常见容器逃逸配置错误。
- 依赖安装、构建脚本和联网行为必须经过策略与 Approval。
- 任务结束、中断或超时后清理全部子进程和临时资源。
- 建立 Windows 主机与 Linux 容器组合下的安全回归套件。

### S2-G6：建立 Git 原生的工作区与审查流程

Agent 应在可恢复、可审查的 Git 边界内工作，并保护用户已有修改。

目标结果：

- 运行前识别 dirty worktree、当前分支、仓库根目录和嵌套仓库。
- 支持为 Session 创建隔离 worktree 或明确选择直接使用当前工作区。
- 不覆盖、不重置或误提交用户已有变更。
- 支持查看分阶段 diff、拒绝局部修改、撤销 Agent 修改和生成提交。
- 测试、最终报告和 commit 使用同一工作区版本，避免验证后漂移。
- 为未来 Issue、PR 和代码审查集成保留稳定接口，但本阶段不要求自动合并 PR。

### S2-G7：提供可持续使用的终端体验

CLI/TUI 应围绕 Session 工作流组织，而不是要求用户手工拼接任务 ID 和离线命令。

目标结果：

- 流式展示模型输出、工具动作、计划进度、测试结果、预算和待审批请求。
- 用户可以随时输入补充消息、中断执行、查看 diff 或切换到审批界面。
- 错误信息给出可执行的恢复建议，不要求用户检查 SQLite 或原始 JSONL。
- 配置来源、Provider、模型、Sandbox、Skill 和权限状态清晰可见。
- 保留适合 CI 的稳定非交互模式和机器可读输出。

### S2-G8：用真实端到端任务证明实用性

第二阶段评测必须从定位切片和小型合成 fixture 扩展到真实仓库工作流。

目标结果：

- 固定不少于 30 个端到端开发任务，覆盖缺陷修复、功能实现、跨文件重构、测试补充和配置迁移。
- 任务来自多个真实或真实规模仓库，并锁定 revision、依赖与验证命令。
- 最终候选配置至少重复运行三次，不选择性报告最佳结果。
- 独立判定代码正确性、变更范围、测试、Agent 状态和用户审批行为。
- 汇总成功率、首次通过率、恢复成功率、工具成功率、Token、费用、时延、无效动作和安全拒绝。
- 失败按照定位、规划、工具、Provider、权限、Sandbox、上下文和验证分类，并驱动后续优化。

SRF-07 已提供一个锁定真实 Python 仓库、revision、依赖、Issue、公开测试和独立断言的三次试用
入口。2026-09-13 三次真实试用均因 20 step 预算耗尽失败且无代码变更，必须保留失败结果。
该入口只是第二阶段完整“30 个任务、5 个仓库”评测的基础设施和首个清单，不计为已通过样本。
当前 Luna 的 PGW 基础工具往返与 PPS 单文件 fixture 通过，也不能替代这一真实仓库验收。

## 4. 阶段量化目标

以下数字是第二阶段退出目标，不是当前成果：

| 指标 | 第二阶段目标 |
| --- | ---: |
| 真实端到端固定任务 | 不少于 30 项，覆盖不少于 5 个仓库 |
| 最终配置重复次数 | 每项不少于 3 次 |
| 端到端独立成功率 | 不低于 70% |
| 已完成任务测试通过率 | 不低于 95% |
| 工具调用成功率 | 不低于 98% |
| 中断或重启恢复成功率 | 不低于 95% |
| 已确认副作用重复执行 | 0 |
| 未授权高风险动作执行 | 0 |
| Sandbox 逃逸回归用例 | 0 个成功逃逸 |
| 单任务 Trace 关键事件完整率 | 100% |
| Provider 协议族 | 至少 2 类，另含 1 个本地兼容路径 |
| Session 快速开始 | 陌生开发者 10 分钟内启动首个会话 |

工具调用成功率需要同时报告策略拒绝、模型参数错误、工具内部错误和命令返回失败，不能通过删除困难工具调用美化指标。Sandbox 指标只适用于文档明确声明的威胁模型，不代表通过专业安全认证。

## 5. 阶段最终验收场景

在一个包含未提交用户修改的真实中型 Python 仓库中，用户启动新的 PatchLoop Session，选择 Provider 和隔离 worktree，并提交一个带测试要求的 Issue。Agent 应能够：

1. 读取项目约束并按需加载相关 Skill。
2. 检索代码、提出计划并开始执行。
3. 对依赖安装、联网或高风险命令生成可恢复的审批请求。
4. 接受用户中途追加的约束并调整计划。
5. 在进程被终止后恢复，不重复已确认写入。
6. 完成跨文件修改并通过公开与独立测试。
7. 展示只包含本次 Agent 修改的 diff，允许撤销或生成 commit。
8. 输出带 Provider 用量、审批、安全、工具、测试和关键证据的可回放报告。

只有完整场景和固定端到端评测同时通过，第二阶段才算完成。

## 6. 范围边界

第二阶段继续坚持单 Agent 优先，以下能力不是退出条件：

- 多 Agent 角色编排和自治协作。
- Web 控制台、移动端和云端任务队列。
- IDE 深度插件和实时代码补全。
- 自动创建、发布或合并远程 PR。
- 支持所有编程语言和构建系统。
- 企业多租户、计费、组织权限和合规认证。
- 宣称 Sandbox 能抵御宿主内核漏洞或通过专业安全认证。

这些能力只有在第二阶段的单 Agent Session、真实评测和安全边界稳定后才进入后续规划。
