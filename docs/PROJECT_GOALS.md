# PatchLoop 项目目标

## 1. 项目定位

PatchLoop 是一个面向真实软件仓库的自主编程智能体。用户通过自然语言描述开发任务，系统在明确的权限边界内完成代码检索、任务规划、文件编辑、命令执行、测试验证和结果总结。

项目的核心不是“调用大模型生成代码”，而是构建一个可靠、可评测、可观测的 Agent Runtime，使模型能够在长流程、强约束和结果可验证的工程环境中持续工作。

## 2. 简历价值目标

项目需要同时证明四类能力：

| 能力维度 | 项目证据 |
| --- | --- |
| AI Agent 设计 | ReAct/Plan-Execute 工作流、工具调用、记忆、反思与失败恢复 |
| 后端与系统设计 | 任务状态机、并发执行、沙箱、权限模型、事件日志和可恢复任务 |
| 代码智能 | AST/符号索引、混合检索、上下文选择、变更影响分析 |
| 工程与实验 | 自动化测试、基准集、消融实验、指标面板和 CI |

最终简历描述必须有可复现数据支撑，避免只写“实现了智能编程助手”。

## 3. 目标用户与使用场景

### 3.1 目标用户

- 希望自动处理重复开发任务的软件工程师。
- 需要在私有仓库中使用本地或企业模型的研发团队。
- 希望研究 Agent 规划、检索和工具使用效果的开发者。

### 3.2 核心场景

- 根据 Issue 修复缺陷并补充回归测试。
- 在现有模块中实现范围明确的小型功能。
- 执行跨文件重构，并确保测试不回退。
- 分析测试失败、定位根因并生成修复补丁。
- 为陌生仓库解释架构、调用链和变更影响。

## 4. 核心产品目标

### G1：建立可闭环执行的 Coding Agent

系统必须完成“理解任务 → 探索仓库 → 制定计划 → 编辑代码 → 运行验证 → 根据反馈修正 → 汇报结果”的完整闭环，而非一次性生成代码。

验收条件：

- 至少支持读取、搜索、编辑、补丁应用、命令执行和测试六类工具。
- 单个任务可执行多轮工具调用，并设置轮次、时间和费用上限。
- 工具失败或测试失败后，Agent 能基于新信息继续处理。
- 所有文件变更都能以统一 diff 展示并支持拒绝或回滚。

### G2：高质量地理解中型代码仓库

系统需要在有限上下文窗口内找到与任务最相关的代码，减少整仓输入带来的成本与噪声。

验收条件：

- 支持文件名、文本、符号和语义检索。
- 为 Python 提供 AST 或语言服务器级别的符号解析；其他语言可逐步扩展。
- 能识别入口、定义、引用、测试文件和配置文件之间的关联。
- 记录每次被选入上下文的代码及其选择原因。

### G3：保证执行安全与过程可控

Agent 执行命令和修改仓库时必须遵循最小权限原则。

验收条件：

- 命令在容器或受限子进程中运行，限制工作目录、环境变量、网络和超时。
- 对删除文件、访问仓库外路径、联网和安装依赖等高风险操作进行拦截或请求人工批准。
- 敏感信息不进入模型上下文或日志。
- 任务可暂停、继续、取消，并能从最近检查点恢复。

### G4：让 Agent 的行为可观测、可解释

系统应提供结构化执行轨迹，便于定位失败原因和展示系统设计能力。

验收条件：

- 记录模型请求、工具调用、耗时、Token、费用、状态变化和错误类型。
- 支持按时间线回放一次任务。
- 最终报告包含修改摘要、验证结果、未解决风险和关键证据。
- 支持将轨迹导出为 JSON，供离线分析和回归评测使用。

### G5：建立可信的评测体系

项目必须用固定任务集和统一判定方式衡量效果，避免只展示少量成功案例。

验收条件：

- 建立不少于 30 个本地可复现任务，覆盖缺陷修复、功能实现和重构。
- 每个任务使用测试结果或明确断言自动判定成功与否。
- 对比至少一个基线方案，例如“无规划”“无语义检索”或“一次性生成”。
- 输出成功率、平均时延、平均 Token、平均费用、工具错误率和首次通过率。

## 5. 分级目标

### 5.1 MVP：必须完成

- Python 仓库支持。
- CLI 交互入口。
- 单 Agent 规划与执行循环。
- 文件、搜索、补丁、Shell 和测试工具。
- SQLite 任务与事件存储。
- 基础沙箱和人工审批。
- 端到端测试与 10 个小型评测任务。

### 5.2 Portfolio：写入简历前必须完成

- AST/符号索引与混合检索。
- 任务中断恢复、预算控制和错误分类。
- OpenTelemetry 或等价的结构化追踪。
- 不少于 30 个任务的可重复评测。
- 基线对比、消融实验和结果可视化。
- 完整 README、架构图、演示视频和技术文章。

### 5.3 Stretch：时间充裕后再做

- TypeScript 或 Go 仓库支持。
- 多模型路由与本地模型支持。
- 多 Agent 角色协作。
- GitHub App、自动读取 Issue 和生成 PR 草稿。
- Web 控制台和远程任务队列。

多 Agent 和精美前端不是首要目标。只有单 Agent 的可靠性和评测体系达标后，才进入扩展阶段。

## 6. 量化成功指标

以下是项目目标值，最终以实际实验结果替换：

| 指标 | MVP 目标 | Portfolio 目标 |
| --- | ---: | ---: |
| 本地任务集成功率 | ≥ 50% | ≥ 70% |
| 已完成任务中测试通过率 | ≥ 80% | ≥ 95% |
| 工具调用成功率 | ≥ 95% | ≥ 99% |
| 任务中断后恢复成功率 | ≥ 80% | ≥ 95% |
| 无关上下文占比 | 建立测量基线 | 较纯文本检索降低 ≥ 30% |
| 相比一次性生成的成功率提升 | 有可复现实验 | ≥ 20 个百分点 |
| 单任务执行轨迹完整率 | 100% | 100% |

指标不应预先写成项目成果。只有完成固定环境下的多次评测后，才可以在简历中引用。

## 7. 非目标与范围边界

- 不追求取代完整 IDE；首版以 CLI 为主。
- 不承诺支持所有编程语言；首版聚焦 Python。
- 不允许默认执行任意系统命令或访问仓库外文件。
- 不把模型自身能力包装成系统成果；简历重点描述运行时、检索、评测和可靠性建设。
- 不以单个演示任务成功作为项目完成标准。

## 8. 最终交付物

- 可安装、可运行的开源代码仓库。
- 一条命令启动的演示环境。
- 系统架构图和关键时序图。
- 至少 30 个任务的评测集、运行脚本和结果报告。
- 3～5 分钟演示视频。
- 一篇技术文章，解释架构、关键取舍、失败案例和实验结论。
- 中英文简历项目描述及面试讲解提纲。

## 9. 简历成果模板

以下内容只能在对应数据真实测得后使用：
