# PatchLoop 提示缓存优化开发计划

## 1. 状态与目标

自 2026-09-04 起，LCM-10 后的真实记忆场景扩展暂时悬挂。当前优先级切换为 DeepSeek 提示缓存优化；在本计划的退出门禁通过前，不新增记忆类型、不扩大真实场景集，也不根据单次模型结果继续调整召回策略。PCO-00 至 PCO-07 已完成对应功能开发与验收。为避免新增能力继续扩大 Runtime 和顶层模块耦合，下一阶段先执行 [提示缓存架构重构计划](PROMPT_CACHE_ARCHITECTURE_REFACTOR_PLAN.md)，当前下一任务为 PCR-00。

本次观察值约为：

| 指标 | Token | 占比 |
| --- | ---: | ---: |
| Provider 提示缓存命中 | 80,000 | 36.2% |
| Provider 提示缓存未命中 | 141,000 | 63.8% |
| 合计 | 221,000 | 100% |

这些数字是 Provider 返回的提示缓存 Token，不是 PatchLoop 的 `memory_retrieval_hits`。后者表示内部记忆记录被召回的数量，两者必须在数据模型、CLI 和文档中保持不同命名。

优化目标不是实现本地响应缓存，也不是牺牲记忆质量来缩短请求。目标是在保持隐藏测试、权限边界、过期事实抑制和任务成功率不退化的前提下，使多步骤调用具有足够长、足够稳定的公共前缀，并减少发送给模型的动态记忆噪声。

## 2. 已定位的主要原因

DeepSeek 的上下文缓存自动启用，并从请求的第一个 Token 开始匹配相同前缀。当前实现存在四类高优先级问题：

1. `AgentRuntime._with_runtime_memory()` 每个模型步骤都把最新分层记忆拼接到第一条 system 消息。任何记忆变化都会使其后的任务目标和历史失去公共前缀。
2. `ContextEngine.build()` 在裁剪发生时也把 `TaskMemory V1` 拼接到第一条 system 消息，降级路径同样会改写最早前缀。
3. 检索器会随查询、相关性和新近度重新选择历史组。即使最终按时间排序，前一轮已有消息仍可能被移除或替换，请求不具备稳定的追加结构。
4. Provider 使用的记忆文本包含查询信号、记录 ID、来源 ID、浮点分数、选择理由、预算分配、修订号和省略项。它们适合审计，却会频繁变化，并非模型完成任务所需的最小上下文。

此外，DeepSeek Provider 已读取 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`，但目前只用它们估算费用，随后丢弃。`ModelUsage`、checkpoint、TaskReport、metrics 和 replay 都无法按步骤呈现缓存命中，因此还不能用证据判断是哪次请求、哪个区段破坏了前缀。

## 3. 设计原则

- 稳定内容必须在前，动态内容必须在后；动态记忆不得再改写第一条 system 消息。
- 一个任务或 cache epoch 内，模型、thinking 配置、工具名称、工具顺序、工具描述和 JSON Schema 都是冻结契约。权限与模式变化由 Runtime 和 Tool Gateway 执行，不通过增删工具表达。
- `AGENTS.md`、任务目标和其他项目指令在 epoch 起点形成内容寻址快照。中途变化只追加通知，在受控边界才加载新快照，不回写已发送前缀。
- Provider 投影和审计投影分离。Trace 保留完整解释，模型只接收执行必需内容。
- 一个缓存周期内采用“冻结前缀 + 追加尾部”，只在明确边界轮换前缀。
- 压缩分为“复用旧前缀生成摘要”和“携带摘要进入新 epoch”两个阶段，摘要请求自身也必须具备缓存命中条件。
- 先补指标再优化，所有收益必须由 Provider 返回的真实命中字段验证。
- 缓存是尽力而为能力，正确性不得依赖缓存存在、持续时间或一定命中。
- 不持久化原始请求或秘密来换取诊断能力，只保存脱敏元数据与不可逆指纹。

### 3.1 目标请求布局

```text
不可变基础前缀
  system instructions
  稳定工具 Schema
  任务与项目指令快照

冻结周期快照
  当前目标与关键约束
  已验证实现状态
  必要的长期记忆摘要

追加式活动日志
  user / assistant
  tool call / tool result
  memory delta
  environment / permission change notice

当前步骤临时尾部
  本轮检索结果
  当前错误
  最新用户输入
```

前三区段只能追加，不能原位更新或重排。当前步骤临时尾部不承诺跨步骤复用；其中需要长期保留的事实必须先归一化为下一条增量，再进入追加式活动日志。

### 3.2 Provider 能力边界

首轮实现仍以 DeepSeek Chat Completions 为验收路径，但缓存契约保持 Provider 中立：

| Provider | 可用控制 | PatchLoop 策略 |
| --- | --- | --- |
| DeepSeek | 自动前缀缓存、命中/未命中 Token；无客户端显式断点 | 依靠精确前缀稳定性和服务端真实用量验收，不伪造 `cache_control` |
| Anthropic | `cache_control`、TTL、cache creation/read Token | 后续 Adapter 可在稳定工具和 system 区段设置显式断点 |
| OpenAI | `prompt_cache_key`、implicit/explicit breakpoint、cache write/read Token | 后续 Adapter 使用稳定会话键与能力探测，不把会话键当作内容匹配替代品 |
| Fake Provider | 无远端缓存 | 使用确定性公共前缀模拟器验证布局不变量 |

不得把 DeepSeek 的 `user_id` 当作通用 prompt cache key，也不得向不支持的 Provider 发送其他厂商的缓存参数。

## 4. 开发任务

### PCO-00：缓存用量契约与可观测基线

状态：已完成（2026-09-04），验收见 [PCO-00 缓存用量契约与可观测基线验收](milestones/PCO_00_ACCEPTANCE.md)。

开发内容：

- 为 `ModelUsage` 增加可选的 `cache_hit_tokens`、`cache_miss_tokens` 和 `cache_write_tokens`，保留“Provider 未报告”与“报告为 0”的区别；DeepSeek 的 write 字段保持未知，不由 miss 值推断。
- 将字段贯通 model step Trace、Runtime checkpoint、TaskReport、TaskMetrics、`status`、`metrics` 和 `replay`。
- 输出逐步骤和累计的命中 Token、未命中 Token、可选写入 Token、命中率及对应费用，不再只给总输入 Token。
- 当 Provider 同时返回三个字段时校验 `input_tokens = cache_hit_tokens + cache_miss_tokens`；协议异常应可观测，但不得导致已完成任务丢失。
- 用刚完成的 20 步真实场景建立基线报告，定位首次大幅前缀分叉的步骤。

完成标准：Fake Transport 和 DeepSeek 响应解析测试覆盖字段缺失、全命中、全未命中、混合命中及不一致数据；中断恢复前后累计值一致；约 80k/141k 的观察结果能在一份任务报告内还原。

### PCO-01：安全的请求指纹与前缀诊断

开发内容：

- 对静态 system 指令、任务/项目指令快照、工具 Schema、冻结周期快照、记忆 Provider 投影、历史消息组及完整请求分别计算不可逆指纹。
- 记录稳定前缀长度和连续步骤间的最长公共前缀；首版可使用确定性字节估算，并同时保留 Provider 实际 Token 结果。
- 新增缓存布局 Trace，按 `cold_start`、`model_or_thinking_change`、`dynamic_system_prefix`、`project_snapshot_change`、`history_reselection`、`tool_schema_change`、`memory_projection_change`、`epoch_rollover` 和 `provider_best_effort` 归因。
- 工具 Schema 使用固定注册顺序和规范化 JSON 序列化，测试证明相同能力集合得到相同指纹。
- 对超过配置阈值的缓存未命中生成单一主因和可选次因；不能归因时明确记录 `unknown`，不得把所有异常归为 Provider 波动。
- 指纹输入必须先经过现有秘密检测；事件不得保存原始提示、API Key、Bearer Token 或仓库敏感正文。

完成标准：给定两次请求，可以从 Trace 判断第一个变化区段；相同请求跨进程生成相同区段指纹；凭据安全测试保持零泄漏。

### PCO-02：稳定前缀请求组装

开发内容：

- 保持静态 system 指令不变，不再向第一条 system 消息追加工作记忆、分层记忆或 `TaskMemory V1`。
- 把任务目标、项目指令快照和稳定工具能力放入可复用前缀，把运行时记忆包装为独立、不可信的动态上下文消息并置于稳定前缀之后。
- 一个任务或 cache epoch 内冻结完整工具面。Plan/Execute、权限和审批状态变化只追加控制消息并由 Tool Gateway 强制执行，不删除、增加或重排模型可见工具。
- `AGENTS.md` 或其他项目指令中途变化时追加带旧/新内容哈希的变更通知；只有显式 epoch 轮换才载入新快照。
- 模型、thinking 参数或 Provider 路由变化必须显式开启新 epoch，并记录预期缓存失效原因，不能作为普通步骤静默变更。
- 统一正常 Memory 2.0、TaskMemory V1 降级和模型评测驱动器的组装方式，避免不同入口重复实现。
- 针对 DeepSeek thinking 与 tool-call 协议验证消息角色和 assistant/tool 原子组不被破坏。
- 引入配置开关，保留旧布局用于 A/B 与快速回退。

完成标准：连续步骤中 system、任务/项目快照和工具 Schema 指纹不变；权限或模式切换不改变工具指纹；记忆和环境变化只追加到动态尾部；现有工具调用、思考模式、审批和安全测试全部通过。

### PCO-03：拆分 Provider 投影与审计投影

开发内容：

- 为 `LayeredMemoryContext` 提供精简、确定性的 Provider 投影；现有完整评分和来源解释继续写入 Trace/replay。
- Provider 投影只保留当前工作状态、选中的有效事实、必要失败经验和明确约束。
- 移除记录 ID、来源 ID、浮点分数、召回理由、预算分配、时间戳、修订号和省略 ID 等模型不需要的诊断字段。
- 按语义类型、稳定作用域和内容哈希确定性排序，避免同一事实集合因检索分数轻微变化而重排。
- 安全过滤必须先于两类投影，任何投影都不得绕过凭据和 Prompt Injection 防线。

完成标准：锁定记忆集合的 Provider 投影快照稳定；Trace 仍可完整解释召回；Provider 记忆 Token 相对当前实现至少降低 30%，记忆质量固定测试不退化。

### PCO-04：缓存周期与冻结前缀脊柱

开发内容：

- 引入 cache epoch。每个周期冻结一段已确认历史作为前缀脊柱，新消息只追加到动态尾部。
- 周期内不得因相关性重排而删除或替换已冻结消息；预算压力先裁剪未冻结尾部。
- 只在上下文阈值、计划阶段切换、成功验证、显式压缩或恢复边界轮换周期。
- 周期轮换采用两阶段协议。第一阶段使用与当前模型请求完全相同的 system、工具 Schema 和历史前缀，只在尾部追加结构化压缩指令，使生成摘要的请求可以复用旧缓存。
- 第二阶段才用新摘要替换旧历史并开启新 epoch。允许进入新 epoch 的首个普通请求发生一次可解释的会话层未命中，但静态 system、任务/项目快照和工具区段仍应保持可复用。
- 压缩摘要使用固定结构，累计保留用户约束、精确路径/符号、关键决策及理由、失败方案、测试结果、未完成事项和下一步；不得把摘要重新当作无来源事实。
- checkpoint 保存 epoch ID、前缀消息 ID 与指纹，恢复后保持相同排序，不因重建产生无意义的缓存失效。

完成标准：100 步模拟任务中，每个周期只有受控前缀轮换；本地模拟证明压缩生成请求完整复用压缩前公共前缀；同一 checkpoint 恢复后的前缀指纹一致；历史原子组、上下文硬预算和过期事实过滤仍满足既有门禁。

### PCO-05：记忆快照与增量发布

开发内容：

- 在 epoch 起点发布稳定记忆快照，此后只把新增或变化的事实、错误、计划和验证结果作为小型增量追加到尾部。
- 只有计划阶段切换、工作区写入、测试结果、事实冲突或替代、安全事件等实质变化才发布增量；普通读取不重复发送完整记忆。
- 关键约束保持 pin；增量合并必须能确定性重建当前记忆视图。
- 为增量设置独立 Token 上限和去重键，防止同一事实在多个步骤重复发布。
- 文件、权限、模式和项目指令变化与记忆增量使用同一追加协议；任何调用方都不得原位更新已经进入缓存前缀的消息。

完成标准：固定 20 步真实场景中的完整记忆重发次数显著下降；快照加增量与当前有效记忆语义等价；恢复重放不重复发布增量。

### PCO-06：缓存感知评测框架

开发内容：

- 为 Fake Provider 增加确定性前缀缓存模拟器，用于精确计算连续请求的公共前缀和合成命中/未命中 Token。
- 真实 Provider 评测直接采集 DeepSeek 报告的字段，不用本地估算替代服务端结果。
- 固定比较六种配置：当前布局、仅稳定前缀、固定工具面、精简 Provider 投影、cache epoch 与缓存安全压缩、完整优化。
- 每种配置执行一次冷启动和至少三次可比较运行；固定模型、fixture、温度、上下文预算和权限，不选择性报告最佳一次。
- 分别覆盖冷启动、预热后连续步骤、权限/环境变化、项目文件变化、显式压缩、checkpoint 恢复和模型切换；模型切换作为预期全失效对照，不计入稳态门禁。
- 报告任务正确率、输入 Token、缓存命中/未命中、命中率、步骤、时延、费用、压缩次数、前缀轮换次数、指纹变化次数和大额未命中归因。
- Provider 能力测试验证 DeepSeek 不发送显式断点参数，Anthropic/OpenAI 的未来 Adapter 只在能力声明支持时序列化各自字段。

完成标准：一条命令生成机器可读矩阵和人类可读摘要；相同本地输入的模拟结果指纹一致；真实运行报告均值、最小值、最大值和逐步瀑布。

### PCO-07：验收、灰度与恢复记忆开发

完整优化配置必须同时满足：

- 真实场景公开测试 1/1、隐藏测试 5/5，越界修改、秘密泄漏和过期事实命中均为 0。
- 三次有效运行的聚合提示缓存命中率不低于 70%，相比 36.2% 观察基线有明确提升。
- 排除冷启动、显式 epoch 轮换和模型切换后，预热普通步骤的缓存命中率中位数不低于 85%。
- 单次提示缓存未命中 Token 不高于 70,000，或相对约 141,000 的基线降低至少 50%。
- system、任务/项目快照和工具 Schema 指纹在 epoch 内的意外变化次数为 0；每次超过阈值的大额未命中均有可验证归因。
- 压缩生成请求在本地模拟中必须完整匹配压缩前固定前缀；真实 Provider 结果单独报告，不因其尽力而为语义伪造确定性通过。
- 总输入 Token 相对当前布局降低至少 20%；如果仅改布局而尚未精简内容，应单独报告，不把缓存命中误写成 Token 减少。
- Memory 2.0 的任务正确率、关键事实召回、过期事实抑制、重复失败和恢复一致性不得低于现有结果。
- 优化通过配置开关灰度；旧路径至少保留一个发布周期，并可在不迁移持久化数据的情况下回退。

只有 PCO-00 至 PCO-07 的门禁全部通过，才恢复新增真实记忆场景和下一阶段记忆能力开发。

## 6. 非目标与风险控制

- 不实现跨任务共享的本地响应缓存。
- 不依赖 Provider 缓存持续时间，不通过无业务意义的保活请求维持缓存。
- 不为了跨任务共享缓存复用用户标识、任务标识或 Provider 隔离字段。
- 不把 API Key、完整提示或原始仓库证据写入缓存诊断事件。
- 不通过固定陈旧记忆来追求命中率；安全和事实有效性优先于缓存复用。
- 不采用每轮把活跃文件全文重写进 system 的 cache-maximal 路径；文件内容通过工具历史或有来源的尾部增量进入上下文。
- 不把价格配置更新与命中率优化混为一个任务；价格按 Provider 官方配置单独版本化。

主要风险是消息角色调整影响 thinking/tool-call 协议、冻结前缀延迟事实失效，以及 Provider 缓存的尽力而为特性造成结果波动。对应控制是协议回归测试、动态增量覆盖与 epoch 轮换、三次以上真实运行及本地确定性缓存模拟。
