# Week 6 验收记录

## 结论

PatchLoop 已于 2026-08-29 通过第六周“上下文与记忆管理”验收。Runtime 在每次 Provider 调用前构建有界上下文，能够压缩旧步骤与大型工具输出，同时通过结构化任务记忆保留早期关键证据和未完成计划。

## 上下文预算

`TaskBudget` 新增以下单次请求约束：

- `max_context_tokens`：消息与工具 Schema 的总估算 Token 上限，默认 32,000。
- `max_tool_output_chars`：单个工具观测进入模型消息的最大字符数，默认 8,000。
- `context_recent_steps`：优先保留的最近完整步骤数，默认 4。

预算构建遵循以下不变量：

1. 系统提示、原始任务目标和 Tool Schema 必须保留。
2. assistant tool call 与对应的全部 tool response 作为原子组保留或省略。
3. 最近步骤优先，其他步骤按任务与未完成计划相关性选择。
4. 最终消息与 Tool Schema 的估算总量不得超过任务预算。
5. 强制内容本身超限时不调用 Provider，以 `budget_exceeded` 终止。

## 结构化任务记忆

被省略的历史不会静默丢弃，而是转换为 `TaskMemory`：

- 原步骤编号。
- `pending` 或 `running` 的计划事项及其证据。
- 按当前目标相关性排序的关键工具证据和文件路径。
- 工具失败摘要。
- 有文本内容的历史决策。

任务记忆以机器生成 JSON 合入系统提示。所有来自仓库和工具的内容明确标记为不可信数据，避免把代码中的指令提升为系统指令。

## 大型工具输出

工具完整结果继续用于最终报告、验证记录、SQLite 恢复和事件审计。进入模型上下文的副本使用确定性头尾截断，并记录：

- 是否截断。
- 原始输出字符数。
- 工具成功状态和错误分类。
- 调用 ID 与工具名。

这样既保留错误尾部和开头证据，也避免一次文件读取或测试日志挤占整个上下文。

## 长任务端到端验收

固定测试使用 900 Token 上下文预算、400 字符工具观测上限和 1 个最近步骤，依次读取 1 个包含早期结论的大文件及 5 个大型噪声文件，然后完成最终回答。

自动断言确认：

- 7 次 Provider 调用的每个上下文估算值都不超过 900。
- 最大上下文估算占用为 867 Token，5 次调用触发历史压缩。
- 6 个大型工具输出全部被截断，Gateway 中仍保留完整结果。
- 早期 `EARLY-CONCLUSION=blue-widget` 被收入后续结构化记忆。
- 最终 Provider 必须看到该早期结论才能返回成功，任务状态为 `completed`。
- 报告记录上下文窗口数、压缩次数、最大占用和工具截断次数。

上述场景的机器可读结果保存在 `benchmarks/results/week06_context.json`，端到端测试会逐字段验证报告，防止实现变化后验收数据静默失真。

## 调试视图

每次调用前发出 `context.built` JSONL 事件，包含预算、消息与工具 Schema 估算量、所选步骤及原因、丢弃步骤、记忆用量和截断数量。

```bash
patchloop context <task-id> --repo /path/to/repository
```

命令先输出紧凑预算条，再输出机器可读的完整调试对象，便于检查某段证据为何保留或被压缩。

## 质量门禁

第六周验收执行 Ruff、mypy、完整 pytest 和分支覆盖率门禁：Ruff 与 mypy 全部通过，pytest 为 55 项通过、1 项因当前 Windows 主机不支持符号链接而跳过，分支覆盖率为 88.29%，高于 85% 门禁。

## 已知边界

Token 预算目前采用保守字符估算，不等同于 DeepSeek 精确 tokenizer；抽取式摘要不具备模型摘要的语义归并能力。完整工具结果仍会进入本地审计与恢复存储，敏感字段脱敏将在第七周安全与可观测性任务中实现。
